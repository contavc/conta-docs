## The threat model, honestly

The useful question is not "is Conta secure?" but "what happens if Conta is
compromised?". Scenario by scenario:

| Scenario | What the attacker gets | What they **cannot** do |
| --- | --- | --- |
| Database leaked | Metadata: profiles, usernames, operation history | Move balances. Claim money links (only SHA-256 hashes of tokens are stored) |
| Conta's server compromised | Hodle API keys, control of operational float | Sign for a user. Move BRLA out of a user wallet |
| Conta shuts down | — | Prevent access to balances: they sit in users' own wallets |
| User's device compromised | **Everything belonging to that user** | Affect any other user |

<Callout type="warn" title="The line that is never crossed">
No compromise of **ours** moves a user's balance. Every compromise of **their
device** does. That is the fundamental trade of self-custody, and the asymmetry
is deliberate.
</Callout>

## What is exposed in a compromise of ours

Worth being specific rather than reassuring. An attacker holding our server
would have access to operational float — the Hodle wallet and the on-ramp
wallet. That is **our** money, not users', but it is real money, and it is why
those wallets carry only the float needed to operate, with minimum-balance
alerts.

They could also fire payouts in Conta's name for as long as the keys were
valid. What they could not do is touch BRLA sitting in a user wallet — because
no signing path to it exists.

## Verifying for yourself

None of this requires trust. Any user's balance is public and auditable in a
block explorer.

<Steps>
<Step>
### Get the wallet address

It is visible in the app, in the account area.
</Step>

<Step>
### Look it up on Base

Open the address on [BaseScan](https://basescan.org) and check the BRLA token
balance.
</Step>

<Step>
### Compare with the app

The number must match the displayed balance — because that is exactly where the
app reads it from.
</Step>
</Steps>

The same holds for any operation: every BRLA transfer made through the app has
an on-chain hash, permanent and verifiable by third parties.

## Practices in the code

<Cards>
  <Card title="Secrets never reach the client" description="Third-party API keys live only on the server. The client talks to our proxy, never directly to Hodle." />
  <Card title="Sensitive headers are never logged" description="Calls to Hodle carry an operational PIN in headers; those are excluded from every log." />
  <Card title="Tokens stored as hashes" description="Money-link tokens exist in cleartext exactly once, in the creation response. The database holds only the SHA-256." />
  <Card title="Money-moving routes fail closed" description="Without its authentication secret configured, the cron route refuses to run rather than executing unprotected." />
</Cards>

## The limit of self-custody

It deserves saying without euphemism: **if a user loses access to their
passkeys, Conta cannot restore the balance.** There is no support-desk
recovery, because there is no copy of the key on our side.

In practice this is mitigated by OS keychain sync (iCloud, Google), which
replicates the passkey across the user's devices. But that mechanism belongs to
the operating system, not to us — and that is precisely what makes the claim
"the money is theirs" true.
